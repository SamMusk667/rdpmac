# 画面暂停、重画与码流录制

2026-09-25 你报告：屏保运行时切换到其他窗口，mstsc 可能出现花屏（截图里整个桌面偏紫偏绿，终端的黑底变成灰绿，文字只剩淡淡
的轮廓）。评估结论是客户端解码器的参考帧和编码器失步：亮度也错了，后面的帧只是把差异叠在一张错的底图上。离线用同一个
编码器模拟"动画切到桌面"并加上随机积压、发送失败、关键帧请求，ffmpeg 解码每一帧都正确，所以问题出在 mstsc 那边或只在
现场出现，现有日志证实不了。损坏留住不走，是因为 rdpmac 从不理会客户端要求重画的请求，画面静止时也不会有关键帧。

据此先做了两件事：响应客户端的暂停与重画请求（A），以及可选的码流录制（C），下次复现时就能确定是码流的问题还是 mstsc
的问题。

## 暂停与恢复（Suppress Output）

mstsc 最小化时发 Suppress Output 请求不要画面，恢复时再发一次允许画面，通常还跟一个 Refresh Rect。IronRDP 收到后只翻一个
标志（`display_suppressed`），rdpmac 以前完全不看。现在：

- 请求持续 1 秒后画面暂停：屏幕采集关闭，什么都不编码、不发送。等 1 秒是因为有的客户端在负载下会来回翻这个标志。
- 连接过程中 mstsc 也会先发一次"不要画面"。所以只有在这一路画面已经发出过、之后客户端又表示过要画面，才会暂停，
  第一帧永远照发。客户端要是一直不收回这个请求，就和以前一样一直发。
- 客户端再要画面时，采集重新打开（新的采集流第一帧就是屏幕当前的样子），这一帧是关键帧；码率从目标值重新开始，
  因为最小化期间客户端不确认帧，积压出来的降速和网络无关。以前 mstsc 转到后台时码率会被压到 500 kbit/s，
  回来后要两分钟左右才恢复清晰。
- 日志：`the client asked for no picture, as mstsc does while minimised; pausing the picture` 和
  `the client wants the picture again; sending all of it`，码率有变化时还有 `H.264 bitrate reset`。

H.264 和 RemoteFX 都这样暂停。测试图案模式也一样，只是没有采集可关。

## 重画（Refresh Rect）

IronRDP 补丁给 `RdpServerDisplay` 加了 `request_refresh`，收到 Refresh Rect 或允许画面的 Suppress Output 时调用。
rdpmac 收到后把当前画面作为关键帧重发：屏幕在变就是下一帧，静止时在下一个空闲时刻发。同一秒内的多个请求只发一次，
恢复画面时附带的那个请求由恢复时的关键帧顶替。日志：`the client asked for the whole picture again`。
RemoteFX 的位图不依赖前一帧，不需要重发。

重画和恢复画面时还会重置客户端的图形状态：发 ResetGraphics，建一个新 surface（日志 `graphics surface created`），
关键帧发到新 surface 上。这样 mstsc 的解码器也从头开始，见下一节。

## 两路视图错位（2026-09-26）

打开录制后又出现三次花屏：锁屏醒来、屏保期间，以及平时看 YouTube 时。录下的码流每一帧都是主视图在前、辅助视图在后，
ffmpeg 零错误解码，合成出来的画面正确；mstsc 也确认了每一帧，已解码计数一帧不差。截图的样子和"把两路视图对调后照常
合成"的模拟完全吻合：整个桌面被压成左右两份半宽的图（辅助视图亮度平面的排列）。所以是 mstsc 把主视图和辅助视图配对
错开了一帧。它用一个解码器依次解两路视图，一旦某一刻晚出一帧，之后就一直错开，关键帧修不好；AVC420 只有一路视图，
晚一帧看不出来。那次在屏幕静下来之后（移动鼠标、预览视频停下）自己恢复了。mstsc 在切换焦点时不发暂停或重画请求。

对应的两处改动：

- 重画和恢复时重置图形状态（上一节）。花屏时把 mstsc 最小化再恢复，应当能让它重建解码器、恢复正常。
- 每一路视图的码流最前面加访问单元分隔符（AUD，NAL 类型 9，6 字节）。H.264 里它是可选的，VideoToolbox 不输出；
  有的解码器靠它确定一帧从哪里开始。这是一次尝试，能不能防住错位要靠实测。

另一个发现：那次花屏时服务端每秒发了约 50 帧。libscreenio 的采集上限是 60 fps，`fps` 设置只用作等帧超时和编码器的
预期帧率，并没有限速，视频内容会以编码器跑得动的速度发出，客户端每秒要解 100 帧 2560x1440 的 H.264。还没改。

## 码流录制（`h264-dump`）

默认关闭。打开方法：在 `~/Library/Application Support/rdpmac/config.toml` 加一行 `h264-dump = true` 再重启服务端，
或命令行加 `--h264-dump`。App 保存设置时会保留这个键，但设置界面里没有它。

- 每一路 H.264 流一个目录：`~/Library/Logs/rdpmac/h264/<开始时的 UTC 时间>-<宽>x<高>-<avc444|avc420>/`。
  日志里有 `recording the H.264 stream dir=…`。
- 码流按关键帧分段：`0001.h264`、`0002.h264`……每段从关键帧开始，能单独解码（`ffmpeg -i 0001.h264 …`）。
  AVC444 的每一帧是主视图后面跟辅助视图，和发给客户端的顺序一样。一段满 64 MB 后，从下一个关键帧开始新的一段。
- 每段旁边有同名的 `.txt`，一行一件事，时间是 UTC，和日志的时间一致：

  ```text
  2026-09-25T22:27:39.005Z frame 0 main 3163 aux 3959 key 1 qp 24     发出的帧：帧号、两路视图字节数、是否关键帧、量化参数
  2026-09-25T22:27:39.005Z ack 0 queue 0 decoded 1                     客户端确认：帧号、队列深度、已解码帧数
  2026-09-25T22:27:46.001Z resumed                                     客户端恢复画面
  2026-09-25T22:27:48.845Z refresh                                     客户端要求重画
  ```

  客户端发了质量报告（QoE）时还有 `qoe` 行。暂停在日志里。
- 每路流的目录最多留约 1 GB，超出后从最旧的段删起；`h264/` 下只留最近 3 个目录，所以最多占约 3 GB。
  屏保这种全屏动画约 15 Mbit/s，1 GB 大约是最近 9 分钟；平时的桌面操作能留几个小时。

复现花屏后请记下时间，尽快（几分钟内）断开连接，把对应的目录发给我，并告诉我是在 Windows 上切换窗口还是在会话里切换
Mac 的窗口。我会用 ffmpeg 解码那段码流，按 AVC444 合成画面：如果录到的码流本身就是花的，问题在编码器；如果解码正常而
mstsc 显示花屏，问题在客户端，再看确认和重画记录判断它丢了什么。

## 测试（2026-09-25）

- 单元测试：暂停只在"已发过画面、客户端要过画面、请求持续 1 秒"之后发生，短暂翻转不算；重画一秒内只发一次，
  恢复后的重画被顶替；编码器 `resend` 把静止画面作为带两路视图的关键帧重发；录制按关键帧分段、超限删旧段、目录只留 3 个；
  UTC 时间格式。
- 回环：临时写了一个基于 IronRDP 的测试客户端，协商到 AVC444 后在第 3 秒发"不要画面"，第 7 秒发"允许画面"加
  Refresh Rect，第 10 秒单独发 Refresh Rect。测试图案下 AVC444：约 1 秒后停发，恢复后第一帧是关键帧，单独的重画后
  立即有一个关键帧；RemoteFX 同样暂停和恢复。录制目录里 274 帧、273 个确认，关键帧正好在 `resumed` 和 `refresh`
  之后，ffmpeg 无错误解码出 548 帧（每帧两路视图）。
- 真实屏幕的采集暂停与重开要屏幕录制权限，本机测试进程没有，留给你用 mstsc 实测：最小化 mstsc 一会儿再恢复，日志里应
  出现上面两行，画面应立即是当前的样子。

## 还不知道的

- mstsc 在"切换到其他窗口"（不是最小化）时发不发这些请求。打开录制后复现一次，日志和 `.txt` 会说明。
- 花屏的根本原因。A 只让客户端要求重画时能恢复；如果 mstsc 花屏时不要求重画，损坏仍会留到下一个关键帧，那时再考虑
  画面静止后补关键帧（评估里的 B）。
