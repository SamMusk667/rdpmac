# AVC444 (M4 item 2)

H.264's 4:2:0 drops half the chroma both horizontally and vertically, so the edges of the strokes
of coloured text blur and darken. This is why coloured text has colour fringes in an AVC420
picture. AVC444 carries the full 4:4:4 chroma in one H.264 bitstream as two 4:2:0 pictures.
Implemented on 2026-09-25; local tests pass. Verified with mstsc the same day: no problems.
Released in 0.3.2.

## Layout

The codec used is AVC444v2 (MS-RDPEGFX 2.2.4.6 and 3.3.8.3.3, codec id 0x000F). A capability set
of V10 or later supports both AVC444 and AVC444v2 unless it carries AVC_DISABLED. A 4:4:4 picture
is split into two views:

- Main view: the luma, plus the average chroma of each 2x2 block; that is, an ordinary 4:2:0
  picture.
- Auxiliary view: the chroma samples the main view leaves out.
  - Y plane: left half, Cb of the odd columns (B4); right half, Cr of the odd columns (B5).
  - U plane: odd rows at columns 4x; left half Cb (B6), right half Cr (B7).
  - V plane: odd rows at columns 4x+2; left half Cb (B8), right half Cr (B9).

The client puts the auxiliary view's samples back in place, and rebuilds the sample at the even
row and column from the average and the other three samples. Where the rebuilt value differs from
the average by less than 30, the client still uses the average, so smooth chroma has small errors
even when both views are lossless. On the test picture below, this limit is Cb 42.6 dB and Cr
40.4 dB.

The layout splits rows into halves and quarters, which only line up with the macroblocks the
client decodes when the width is a multiple of 16. So AVC444 is used only when the width is a
multiple of 16 and the height is even; other sizes (1366x768, for example) use AVC420.

## One bitstream, two prediction chains

The specification requires both views to be encoded by the same encoder and decoded by the same
decoder as one bitstream. VideoToolbox's hardware encoder predicts only from the frame before, and
the two views alternate, so the frame before is always the other view, which looks nothing like
it. Measured on a 1920x1200 picture of coloured text, the auxiliary view took 266 KB on every
keystroke, nearly as much as an intra-coded frame.

The solution is VideoToolbox's long-term references (LTR):

1. The session sets `ReferenceBufferCount` to 5 and `EnableLTR`. On macOS 26, 4 is enough (with 3,
   only every other frame becomes a long-term reference; with 2, none does). macOS 27 keeps one
   fewer: with 4, every third frame comes without a token, and the next view of its kind has no
   reference and costs nearly an intra-coded frame. So it is now 5; see "Reference frames and
   mstsc" below.
2. After each frame is encoded, its LTR token is taken from the sample attachments and kept
   separately for each view.
3. When the next view of the same kind is encoded, its frame options acknowledge the token of the
   last view of that kind and ask for `ForceLTRRefresh`. A refresh predicts from the most recently
   acknowledged long-term reference, and the one just acknowledged is the last view of the same
   kind.
4. After a key frame both chains start over.

So each view costs only what changed since the last view of its kind. Measured on the same Mac
with the same 1920x1200 picture:

| Scenario | Main view | Auxiliary view |
|---|---|---|
| First frame (key frame) | 388 KB | 266 KB |
| Typing one character | 0–5 KB | 0–16 KB |
| After continued typing | 0–2 KB | 0–3 KB |
| One step of a scroll (20 rows a frame) | 4–18 KB | 2–22 KB |

### Frame timing

VideoToolbox drops a long-term reference that is not acknowledged soon enough. It estimates the
frame interval from presentation times, and a long-term reference still unacknowledged after about
5 frame intervals is no longer used for prediction. Timed in real time, the refinement frame 0.2
seconds after the picture goes still is already 6 intervals later, so its auxiliary view falls
back to intra coding again: this is why refinement frames were always 458 KB in the first
implementation. In controlled tests the interval counted frames, not milliseconds: a reference 7
frames back was dropped though only 23 ms had passed, and one 2 frames back was kept though 667 ms
had passed. So the AVC444 encoder's presentation times are a frame count that goes up by one for
each frame. AVC420 still uses real time, which VideoToolbox's own rate control needs; AVC444
always uses a per-frame quantiser.

### Reference frames and mstsc

Earlier, mstsc disconnected at 1920x1200 (0x1108) because the SPS did not set
`max_dec_frame_buffering`, so the decoder prepared a 12-frame buffer for level 5.0. The same
version worked at 1920x1080, which is level 4.0 and implies 4 frames. Since the fix, the SPS's VUI
states a buffer equal to the number of reference frames.

VideoToolbox never declares more reference frames than the level allows. Choosing the level
itself, it takes level 4.0 for 1920x1080 and 1680x1050, which holds only 4 frames, and cuts the 5
reference frames to 4. So an AVC444 session asks for Main 5.0 when the picture fits level 5.0
(22080 macroblocks); larger pictures still leave the level to VideoToolbox. The SPS as read with
ffmpeg on macOS 27 on 2026-09-26:

| Size | Level | Reference frames | Level holds |
|---|---|---|---|
| 1280x720 to 2560x1600 | 5.0 | 5 | 6 to 22 |
| 3840x2160 | 5.1 | 5 | 5 |
| 4096x2304 | 5.2 | 5 | 5 |

ffmpeg decoded all the scroll scenario's bitstreams without errors. AVC420 is unchanged (2
reference frames, level chosen by VideoToolbox).

## Both views in every frame

Every change of the picture is encoded as both views, sent together in one
RFX_AVC444V2_BITMAP_STREAM (LC=0); refinement works the same way. The first design sent only the
main view while the picture changed (LC=1), and added an auxiliary view once it was still (LC=2).
It was dropped for two reasons:

- The region is the whole screen. A client that receives a frame with only the main view takes the
  chroma of the whole screen back to 4:2:0, so every character typed would blur all the coloured
  text on the screen for a moment, until the auxiliary view arrived and sharpened it again.
- The auxiliary view could only be predicted from the other view, so every pause would resend a
  whole view, 266 to 458 KB.

When VideoToolbox occasionally drops an auxiliary view, that frame goes out with the main view
only; the client shows it in 4:2:0 and recovers with the next frame.

## Main view only under sustained motion (2026-09-26)

AVC444 has the client decode two pictures for every frame: 2560x1600 at 30 fps is like decoding 4K
at 30 fps continuously. During sustained motion over large areas, such as a screen saver animation
or YouTube, mstsc on five occasions showed the auxiliary view as the main picture (the whole screen
became two half-width, off-colour copies). Key frames did not repair it; it recovered after mstsc
was minimised and restored and the server moved to a new surface. The server encodes the two views
into its bitstream in order and synchronously, and ffmpeg decodes that bitstream without errors, so
the problem is in the client; all the server can do is give it less to decode.

- 23 or more changes of the picture within 1.5 seconds (15 frames a second) count as sustained
  motion: the encoder encodes the main view only (`set_main_only`), and the server moves to a new
  surface and sends AVC420, starting with a key frame. The main view is itself a 4:2:0 picture,
  and main views still predict from each other through long-term references. Log:
  `the picture keeps changing; sending the main view only, as AVC420`.
- Once the picture has been still for 1 second (checked in `refine`), the server moves to a new
  surface and sends the newest picture again in both views, starting with a key frame. Log:
  `the picture is still; sending it in full colour again`. Typing (a few times a second) does not
  trigger the switch.
- During motion, coloured text is in 4:2:0 and slightly blurred; video is 4:2:0 to begin with, so
  it looks no different. Each switch costs one more key frame. When the client comes back from
  being minimised, it starts again with AVC444.
- The decoding times in mstsc's QoE reports are logged every 10 seconds in a line
  `client decoding time median_ms=… max_ms=… frames=…` (timeDiffEDR; FreeRDP sends no QoE). With
  `h264-dump` on, the switches also go into the recording's index (`main view only` /
  `both views`).
- Loopback: FreeRDP `/gfx:avc444` connected to `--test-pattern` (temporarily changed to move for 3
  seconds and stay still for 3). It switched to the main view only after 0.74 seconds, and back to
  both views once the picture had been still for 1 second: two rounds back and forth, each switch
  with a new surface and a key frame. The client reported no errors, and ffmpeg decoded the
  recording without errors.

## Colour conversion

vImage converts BGRA to full-range BT.709 4:4:4 and splits it into planes: the luma goes straight
into the main view's buffer, and the chroma goes to the packing code in bands of 64 rows. The
packing code writes the main view's averaged chroma and the auxiliary view's samples. Both views'
buffers come from the encoding session's buffer pool. The auxiliary view is kept with the picture,
so refinement does not pack it again.

The packing loops write fixed-size chunks, which the compiler turns into vector instructions. A
picture arrives once every frame interval, and the CPU clocks down between frames, so the same
conversion is then two to three times slower: at 1920x1200 it takes 2.3 ms run back to back and
4.1 ms run once per frame interval.

## When it is used

- `codec = "auto"` (the default): AVC444v2 when the client supports AVC444 and the size fits, else
  AVC420; RemoteFX when the client has no H.264. When the encoder cannot be set up for AVC444 (no
  low-latency hardware encoding or no long-term references), it falls back to AVC420, and the log
  says why.
- `codec = "avc420"`: AVC420 only, at about half the encoding cost of AVC444.
- `codec = "remotefx"`: no H.264.

The app's settings used to have an H.264 switch; it is now a choice of three codecs. The old
switch could only write `auto` or `remotefx`; with the choice, saving no longer changes `avc420`.
`H.264 encoder ready ... avc444=true` and
`sending H.264 through the graphics pipeline ... codec="AVC444v2"` in the log show that AVC444 is
in use.

Changing between AVC444 and AVC420 in the app, or changing the colour conversion
(`parallel-conversion`), does not restart the server on saving: the control socket works out the
settings from the command line plus the new file and hands them to the graphics pipeline, which
applies them from the start of the next connection; the current connection stays as it is. The
button then reads "Save", otherwise "Save and Restart Server". Changing to or from RemoteFX still
needs a restart, since whether the graphics pipeline is offered is decided when the server starts.
Editing config.toml directly takes effect only after a restart.

## Tests (2026-09-25)

- Unit tests: the layout restores 4:4:4 chroma as the specification describes (the reverse filter
  and the threshold included); the 4:4:4 conversion is correct across bands; the AVC444 encoder
  puts both views in every frame, and when typing, after a pause, on refinement and after a key
  frame, both views cost only what changed. The pause case fails if the timing is changed back to
  real time, so it guards against the problem above.
- Bitstream check: encoded with `h264_probe` (argument `avc444`); ffmpeg decodes the whole
  bitstream as one stream, which is then restored to 4:4:4 the way the client does it and compared
  with the original. The test picture is a 1920x1200 desktop screenshot: a grey settings sidebar
  down the left, and the rest of the screen full of coloured log text:

  | | Y | Cb | Cr | RGB | Pixels off by more than 40 |
  |---|---|---|---|---|---|
  | AVC420, still, after refinement | 49.1 dB | 31.8 dB | 29.5 dB | 28.4 dB | 4.12% |
  | AVC444v2, still, after refinement | 49.1 dB | 40.9 dB | 38.9 dB | 37.0 dB | 0.43% |
  | AVC444v2, stopped after a second of scrolling | 49.1 dB | 40.8 dB | 38.9 dB | 36.9 dB | 0.45% |
  | AVC444v2, stopped after repeated full-screen inversions | 48.7 dB | 40.8 dB | 38.7 dB | 36.7 dB | 0.47% |

  The chroma is within 2 dB of the layout's own limit. At 4x magnification, AVC420's magenta and
  blue text is dark and bleeds into the background; AVC444 cannot be told apart from the original.
- FreeRDP loopback: `sfreerdp /gfx:avc444` connected to rdpmacd running `--test-pattern`. At
  1920x1080 it negotiated V10.7 and used AVC444v2, and the client decoded without errors; 1366x768
  fell back to AVC420, as the rule says.

## Cost

Time per frame in `h264_probe`'s scroll scenario, from getting the picture until both views'
bitstreams are encoded (median):

| Size | AVC420 | AVC444v2 |
|---|---|---|
| 1920x1200 | 10 ms | 20 ms |
| 3840x2160 | 27 ms | 55 ms |

The hardware encodes in order: submitting both views together and waiting once is no faster. At
4K, hardware encoding of the two views alone takes 36 ms, so while the whole 4K screen keeps
changing AVC444 runs at about 18 fps and AVC420 still at 30 fps; at 1920x1200 both views fit
within the frame interval of 30 fps.

### Colour conversion on several cores (2026-09-25)

The colour conversion can be split across several threads: the picture is cut into strips of whole
bands (64 rows), and each thread converts one strip and writes both views for it. The number of
threads is the number of available cores, at most 6. Total time per frame in the same scroll
scenario (median):

| Threads | 1920x1200 | 3840x2160 |
|---|---|---|
| 1 | 21 ms | 54 ms |
| 2 | 19 ms | 52 ms |
| 4 | 18 ms | 49 ms |
| 6 | 18 ms | 46 ms |
| 8 | 18 ms | 48 ms |

At 4K the conversion drops from 13.5–16 ms to about 8.5 ms, while the two hardware encodes stay at
18 ms each, so the whole frame is only 10% to 15% faster. It is on by default;
`parallel-conversion = false` or the switch in the app turns it off, for comparison in real use.

## Known limitations

- At 4K, continuous changes over large areas get a lower frame rate than with AVC420; see the
  table above. Under sustained motion only the main view is sent now, but for a little over the
  first second of motion both views still go out.
- The region is always the whole screen. Once ScreenCaptureKit's dirty rectangles are wired in,
  both views can report only the regions that changed.
